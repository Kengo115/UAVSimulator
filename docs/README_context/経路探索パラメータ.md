# PS/EPS 経路探索パラメータ解説

最終更新: 2026-08-04

---

## 概要

Physarum Solver（PS）とその派生手法（EPS・PG-EPS）は、粘菌の管ネットワーク形成を模倣した生物模倣アルゴリズムである。本ドキュメントでは各パラメータの意味・役割・チューニング指針を説明する。

対象クラス:
- `AbstractPhysarumSolverRouteSearcher` — 基底クラス（共通パラメータ）
- `ExtendedPhysarumSolverRouteSearcher` — EPS実装（`updateTubeThickness`）
- `BisectionalPressureGuidedEPSRouteSearcher` — 現在の主要手法（PG-EPS）

---

## アルゴリズムの基本原理

各リンクを「チューブ」とみなし、フローが多く流れるチューブほど太くなる（正のフィードバック）。太いチューブはコンダクタンスが高いため、さらにフローを引き寄せる。この自己強化により、最適な経路に自然と収束する。

**1イテレーション内の処理:**

1. **圧力方程式を解く**: チューブ厚に基づくコンダクタンス行列で線形方程式 `AP = Q` を解く
2. **フロー計算**: 各リンクの流量 `Q = D/L × (P_i - P_j)` を計算
3. **シグモイド変換**: `Q_sigmoid = |Q|^γ / (1 + |Q|^γ)` （後述のGAMMAを参照）
4. **チューブ厚更新**: `D_new = D_old + dD/dt × tanh((capacity - flow) × coefficient_tanh)`

収束後、フロー分解アルゴリズム（BFS → グリーディ探索）で整数台数のUAVに経路を割り当てる。

## 基底クラスパラメータ（`AbstractPhysarumSolverRouteSearcher`）

```java
protected static final double DELTA_TIME        = 0.02;
protected static final double GAMMA             = 1.01;
protected static final double coefficient_tanh  = 1.0;
```

---

### DELTA_TIME = 0.02

**役割:** チューブ厚 ODE の積分ステップ幅（前向きオイラー法）

チューブ厚の更新式:
```
D_new = D_old + dD/dt × Δt × tanh(...)
```

`dD/dt` は各リンクの流量に基づいて計算される微分値であり、`DELTA_TIME (Δt)` が実際の更新量の倍率となる。

| 値 | 効果 |
|---|---|
| 小さい（例: 0.01） | 1イテレーション当たりの変化量が小さい。安定だが収束に多くのイテレーションが必要 |
| 大きい（例: 0.02） | 変化量が大きくなり収束が速まる。ただし過大にすると振動リスクあり |

> **現在値の根拠:** 0.02 × 500イテレーション = 10 物理時間単位。0.01 × 500 = 5 単位と比較して2倍の時間進化が得られる。

---

### GAMMA = 1.01

**役割:** シグモイド変換の指数

```java
Q_tubeFlow_sigmoidOutput[i][j] = |Q|^γ / (1 + |Q|^γ)
```

大きいと `|Q|=1` 前後でより急峻なS字カーブになる。

**BisectionalPGEPS での影響:** なし

`Q_tubeFlow_sigmoidOutput` 配列は計算されるが、`ExtendedPhysarumSolverRouteSearcher.updateTubeThickness()` はこの配列を参照しない。`GAMMA` を変更しても BisectionalPGEPS の収束には影響しない。

---

### coefficient_tanh = 1.0

**役割:** チューブ厚更新時の容量制約の鋭さを制御

```java
double tanhValue = Math.tanh((capacity - flow) * coefficient_tanh);
double newThickness = oldThickness + D_tubeThickness_deltaT[i][j] * tanhValue;
```

`tanh` の入力を `(capacity - flow)` とすることで:
- `flow < capacity`（容量に余裕）→ `tanhValue > 0` → チューブを太らせる
- `flow = capacity` → `tanhValue = 0` → 変化なし（均衡点）
- `flow > capacity`（容量超過）→ `tanhValue < 0` → チューブを細らせる

`coefficient_tanh` の値が大きいほど `tanh` の立ち上がりが急峻になり（より二値的な挙動）、各チューブが「使う/使わない」を早期に決定するため収束が速まる。ただし `DELTA_TIME` との組み合わせで振動が起きる可能性がある。

| 値 | 効果 |
|---|---|
| 0.5 | なだらかな遷移。安定だが収束が遅い |
| 1.0 | 急峻な遷移。収束が速い（デフォルト） |
| 2.0以上 | 非常に急峻。振動・不安定化のリスクが高まる |

> **EPSの特徴:** coefficient_tanh が EPS を PS と区別する最重要パラメータ。PS では容量制約なし（`tanhValue`を使わない）。EPS では容量いっぱいまでフローを流す挙動が `tanh((capacity - flow) × coefficient_tanh)` によって実現される。

## BisectionalPGEPS 固有パラメータ

```java
// BisectionalPressureGuidedEPSRouteSearcher
private static final int    MAX_ITERATIONS                   = 5000;
private static final int    REQUIRED_STABLE_ITERATIONS       = 500;
private static final int    MAX_BINARY_SEARCH_ITERATIONS     = 10;
private static final double MIN_ASSIGNMENT_RATIO             = 1.0 / 4.0;  // 25%
private static final double SOURCE_PRESSURE_EMERGENCY        = 100;
private static final double SOURCE_PRESSURE_CHANGE_THRESHOLD = 0.50;       // 50%
private static final double SOURCE_PRESSURE_REDUCTION_THRESHOLD = 0.50;    // 50%
```

---

### MAX_ITERATIONS = 5000

EPSメインループの上限回数。`REQUIRED_STABLE_ITERATIONS` に達せずこの値に到達した場合も、その時点のフロー分布で経路割り当てを実行する（グリーディ探索フォールバックの可能性が高まる）。

`REQUIRED_STABLE_ITERATIONS` と整合する十分な値に設定すること。

---

### REQUIRED_STABLE_ITERATIONS = 500

**収束判定の中核パラメータ。**

フロー変更イベント（後述の3優先度いずれか）が1件も発生しない状態が `REQUIRED_STABLE_ITERATIONS` 回連続した場合、収束と判断してEPSループを終了する。

- フロー変更が発生するたびに `stableIterationCount` は **0 にリセット**される
- 「500回連続してフロー変更なし」= チューブ厚が十分に成熟した状態

| 値 | 効果 |
|---|---|
| 200（旧値） | 早く終了するが、最短経路への収束が不完全になりやすい |
| 500（現値） | より成熟した収束が得られ、最短経路への割り当て率が向上する |

> **実測:** 200→500の変更だけで最短経路への割り当て率が有意に改善することが確認済み。

---

### フロー制御の3優先度

BisectionalPGEPS は以下の3段階でフローを動的制御しながら収束を目指す:

| 優先度 | 条件 | 処理 | `stableIterationCount` |
|---|---|---|---|
| 1（緊急）| `|P_source| >= SOURCE_PRESSURE_EMERGENCY (100)` | フローを二分探索で削減 | リセット |
| 2（フロー減少）| 圧力変化率 >= `SOURCE_PRESSURE_CHANGE_THRESHOLD (50%)` | フローを二分探索で削減 | リセット |
| 3（フロー増加）| 圧力変化率 <= `-SOURCE_PRESSURE_REDUCTION_THRESHOLD (50%)` | フローを1台増加 | リセット |
| （安定）| 上記いずれも非該当 | 何もしない | +1 |

`stableIterationCount` がいずれの優先度でも変更発生でリセットされるため、真の収束は「全優先度において変更が発生しない状態が500回継続」を意味する。

---

### SOURCE_PRESSURE_CHANGE_THRESHOLD = 0.50
### SOURCE_PRESSURE_REDUCTION_THRESHOLD = 0.50

各フロー変更後の基準圧力と現在圧力を比較し、変化率が閾値を超えた場合に次の制御アクションを起動する。

- 0.50 = 前回フロー変更後の圧力から50%以上変化した場合にフロー再調整
- 値を下げると → より敏感に反応（調整頻度増加、収束に時間がかかる場合がある）
- 値を上げると → 鈍感に反応（調整頻度減少）

---

### MAX_BINARY_SEARCH_ITERATIONS = 10

フロー値の二分探索（`lowerBound` ～ `upperBound`）の最大繰り返し回数。収束しない場合に無限ループを防ぐ。通常変更不要。

---

### MIN_ASSIGNMENT_RATIO = 0.25（25%）

EPSで割り当て可能な最小比率。要求UAV台数の25%未満しか割り当てできない場合、グリーディ探索（`adjustRemainingFlowRedis`）に完全移行する閾値。

---

## グリーディ探索フォールバックとは

EPS収束後にフロー分解で経路を割り当てる際、Phase 1（BFS、フロー≥1.0のリンクを使用）で全台数を割り当てられなかった場合、Phase 2（グリーディ探索）で残りを補う。

グリーディ探索では「最大ボトルネックフロー」を優先するダイクストラ的探索を使用し、必ずしも最短経路にはならない。

**グリーディ割り当てが増える原因:**
- `REQUIRED_STABLE_ITERATIONS` が小さすぎる（収束前に終了）
- `MAX_ITERATIONS` に達している（イテレーション上限不足）
- UAV台数がネットワーク容量に対して多すぎる

---

## チューニングガイド

**最短経路への割り当て率を上げたい場合:**

| パラメータ | 方向 | 効果 | リスク |
|---|---|---|---|
| `REQUIRED_STABLE_ITERATIONS` | 増加（例: 500→700） | より成熟した収束 | 計算時間増加 |
| `MAX_ITERATIONS` | 増加（例: 5000→8000） | 上限に達しにくくなる | 計算時間増加 |
| `DELTA_TIME` | 増加（例: 0.01→0.02） | 1イテレーション当たりの進化量増加 | `coefficient_tanh`との兼ね合いで振動リスク |
| `coefficient_tanh` | 増加（例: 0.5→1.0） | 容量制約の判定が鋭くなる | 過大にすると振動 |

> **注意:** `DELTA_TIME` と `coefficient_tanh` はどちらも「反応を強める」パラメータであり、両方を同時に大きくすると振動しやすくなる。片方ずつ調整することを推奨する。

**現在の推奨設定（実験的に効果確認済み）:**

```java
// AbstractPhysarumSolverRouteSearcher
protected static final double DELTA_TIME       = 0.02;
protected static final double coefficient_tanh = 1.0;
// GAMMA = 1.01 は変更不要（BisectionalPGEPS に影響しない）

// BisectionalPressureGuidedEPSRouteSearcher
private static final int MAX_ITERATIONS             = 5000;
private static final int REQUIRED_STABLE_ITERATIONS = 500;
```
