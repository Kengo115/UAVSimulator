## 概要

本シミュレータは，UAV経路探索・管制を担う **Operator** と，UAV飛行処理を担う **NetworkManager** を独立したコンポーネントとして設計し，両者の協調方式として以下の3種類を実装・比較する．

| モード | 協調方式 | 実装パッケージ |
|---|---|---|
| **Redisモード** | Redisキュー + Pub/Sub（イベント駆動） | `operator/`, `network_manager/`, `shared/` |
| **MemoryEventDrivenモード** | インメモリキュー（イベント駆動） | `legacy/eventdriven/` |
| **MemoryPollingモード** | インメモリキュー（ポーリング） | `legacy/polling/` |

本ドキュメントは，この設計判断をソフトウェアアーキテクチャ・ソフトウェア工学の観点から体系的に記述し，学術論文における論理展開の根拠を整理することを目的とする．

## ソフトウェアアーキテクチャ原則との対応

### 2.1 関心の分離（Separation of Concerns）

Dijkstra [1] が提唱した「関心の分離」原則は，システムを互いに独立した責務ごとに分割することを求める．本システムでは以下の対応が成立している．

```
┌────────────────────────────────────────────────────────┐
│  Operator（経路探索・管制）                              │
│   - 経路アルゴリズム選択（Dijkstra / PS / PG-EPS 等）   │
│   - クライアント割り当て                                │
│   - リンク容量参照                                      │
└──────────────────────────┬─────────────────────────────┘
                           │  境界: Redisキュー / インメモリキュー
┌──────────────────────────▼─────────────────────────────┐
│  NetworkManager（飛行シミュレーション）                  │
│   - UAV飛行物理モデル                                   │
│   - リンク容量増減（原子操作）                           │
│   - 待機UAVの再開制御                                   │
└────────────────────────────────────────────────────────┘
```

この分離により，**経路探索アルゴリズムの変更がNetworkManagerに波及せず**，また**飛行物理モデルの精緻化がOperatorに波及しない**という独立性が保証される．

### 2.2 SOLID原則

Robert C. Martin [2] が体系化したSOLID原則のうち，本設計に特に関連するものを示す．

#### 単一責務原則（SRP: Single Responsibility Principle）

各コンポーネントが単一の変更理由のみを持つことを要求する．

| クラス | 責務 | 変更理由 |
|---|---|---|
| `DijkstraRouteSearcher` | Dijkstra法による経路計算 | アルゴリズム改良のみ |
| `FlightScheduler` | UAV飛行イベントスケジューリング | 飛行物理モデル変更のみ |
| `LinkCapacityManager` | リンク容量の原子的増減 | 容量管理ロジック変更のみ |
| `WaitingUAVManager` | 待機UAVのキュー管理 | キュー戦略変更のみ |

#### 依存性逆転原則（DIP: Dependency Inversion Principle）

上位モジュール（Operator）と下位モジュール（NetworkManager）が共に具体実装ではなく抽象（Redisキューインタフェース）に依存する構造となっている．

```
Operator          ──依存──▶  UAVJobQueue (抽象インタフェース)
NetworkManager    ──依存──▶  UAVJobQueue (抽象インタフェース)
                                    │
                          ┌─────────┴─────────┐
                    Redisキュー        インメモリキュー
```

この結果，**OperatorとNetworkManagerが互いに直接依存しない**構造が実現されている．

#### 開放閉鎖原則（OCP: Open/Closed Principle）

Redisを介した設計では，Operatorを変更せずに新しいNetworkManagerコンシューマ（統計収集，リアルタイム監視など）を追加できる．これはRedisのPub/Subメカニズムによって実現される．

### 2.3 疎結合・高凝集（Loose Coupling / High Cohesion）

Yourdon & Constantine [3] が確立した「疎結合・高凝集」の原則は，ソフトウェア設計品質の基礎的指標とされる．

**結合度の分類**（低い順）:
1. データ結合（最低，望ましい）
2. スタンプ結合
3. 制御結合
4. 共通結合（グローバル変数など）
5. 内容結合（最高，避けるべき）

本システムのOperator↔NetworkManager間の結合は**データ結合**（`UAVJob` データ構造のみを共有）に分類される．これに対し，MemoryPollingモードでは `Link[][]` 配列をOperatorとFlightControllerが直接共有するため**共通結合**に近い状態となる．

```
Redisモード:     Operator → [UAVJob データのみ] → NetworkManager  # データ結合
MemoryPolling:   Operator → [Link[][] 共有] → FlightController   # 共通結合
```

### 2.4 イベント駆動アーキテクチャ（EDA: Event-Driven Architecture）

Hohpe & Woolf [4] によるエンタープライズ統合パターンでは，**メッセージキューを用いたコンポーネント間の非同期通信**がシステムの疎結合化と応答性向上の基本パターンとして位置づけられている．

```
[ポーリング方式]
Producer ──▶ Queue ←── Consumer（定期的にキューを確認）
                         ↑ N秒ごとにポーリング

[イベント駆動方式]
Producer ──▶ Queue ──▶ Consumer（キューに積まれたとき即時処理）
                         ↑ ブロッキング待機（BRPOPなど）
```

Redisモードでは `BRPOP`（ブロッキングポップ）により，ジョブ到着と同時に `AsyncUAVWorker` が起動する．これは**反応時間がゼロ**のイベント駆動であり，理論的に検知遅延が発生しない．

## アーキテクチャ構成の比較

### 3.1 Redisモード（本実装の主要設計）

Redisを中央データストアとして使用し，OperatorとNetworkManagerを完全に分離する．

```
┌─────────────────────────────────────────────────────────────────┐
│ Operator (operator/)                                            │
│  RouteSearcher ──▶ UAVJobQueue ──▶ Redis (jobs:uav)            │
└────────────────────────────────────┬────────────────────────────┘
                                     │ BRPOP
┌────────────────────────────────────▼────────────────────────────┐
│ NetworkManager (network_manager/)                               │
│  AsyncUAVWorker ──▶ FlightScheduler ──▶ LinkCapacityManager    │
│                          │                  (Lua原子操作)        │
│                          └──▶ WaitingUAVManager                │
└─────────────────────────────────────────────────────────────────┘
```

**原子性の保証**: `LinkCapacityManager` はLuaスクリプトを用いてRedis上で「容量チェック→消費」を単一の原子操作として実行する [5]．これにより，複数ワーカーが同一リンクに同時アクセスした際の競合状態（Race Condition）を排除する．

### 3.2 MemoryPollingモード（比較対象）

Redisを排除し，`Link[][]` をJVMヒープ上で直接共有する．ポーリングスケジューラが一定間隔でUAV位置を一括更新する．

```
┌─────────────────────────────────────────────────────────────────┐
│ 単一JVMプロセス                                                  │
│                                                                  │
│  RouteSearcher                                                   │
│      │ decrementCapacity()                                       │
│      ▼                                                           │
│  Link[][] (synchronized メソッド)  ◀──── PollingUAVFlightController│
│      ▲                                        │                  │
│      │                              1秒ごと  │ ScheduledExecutor  │
│  flyingUavQueue / uavQueue ◀────────────────┘                   │
└─────────────────────────────────────────────────────────────────┘
```

本モードではper-UAVトランザクション方式（各UAV処理ごとに即時 `decrementCapacity()`/`incrementCapacity()`）を採用し，`Link.capacity` 操作を `synchronized` メソッドで保護することで，同一JVM内でのスレッド安全性を確保している．

### 3.3 モード比較表

| 評価軸 | Redisモード | MemoryPollingモード |
|---|---|---|
| **コンポーネント結合度** | データ結合（低） | 共通結合（高） |
| **飛行時間計測精度** | 高（検知遅延ゼロ） | 低（ラグ ∈ [0, ポーリング間隔]） |
| **水平スケーラビリティ** | ワーカー数追加で向上 | 単一スレッド（構造上不可） |
| **外部観測可能性** | redis-cli で状態確認可 | JVMヒープ内のみ |
| **運用複雑性** | Redis起動が必要 | 不要 |
| **原子性保証** | Luaスクリプト（完全） | synchronized（JVM内のみ） |
| **障害分離** | コンポーネント単位 | プロセス全体に波及 |

## 設計上のトレードオフ

### 4.1 Redisを採用することの利得

#### スケーラビリティ

Kleppmann [5] は，外部メッセージブローカーを介した設計が「コンシューマの水平スケールを可能にする」と論じている．本システムでは，Redisキューを共有する `AsyncUAVWorker` のインスタンス数を増やすことで，UAV処理能力を線形にスケールできる．

#### 観測可能性（Observability）

Redisに格納された状態（`link:{src}:{dst}:capacity`，`waiting:link:{from}:{to}` 等）は，シミュレーション実行中に外部から `redis-cli` を用いてリアルタイムに確認できる．これはデバッグ・実験の再現性に寄与する．

#### 分散展開への対応

Operatorプロセスとnetwork_managerプロセスを異なるホストに配置することが，アーキテクチャ変更なしに実現できる．これは将来的な実機統合（シミュレータをクラウド，UAV制御をエッジに配置するなど）への拡張性を意味する．

### 4.2 Redisを採用することのコスト

- **運用依存性**: Redisサービスが起動していなければシミュレーションを実行できない
- **IPC（プロセス間通信）オーバーヘッド**: ローカルホスト通信であっても，ソケット経由のシリアライズ/デシリアライズが発生する
- **単一障害点**: Redisプロセスの停止がシステム全体の停止につながる

### 4.3 機能的等価性の確認

本実験において，MemoryEventDrivenモード（インメモリイベント駆動）はRedisモードと**機能的に等価**である（検知遅延ゼロ，同一の制御フロー）．これは，Redisの利点が「計算論的性能」ではなく「アーキテクチャ上の構造的性質」にあることを示す．

## 定量的評価指標

ポーリング方式のアーキテクチャ的コストを実証するため，以下の指標を定量的に測定する．

### 5.1 ポーリングラグ（主要指標）

```
lag = realFlightTime - distance / speed
```

| モード | 理論値 |
|---|---|
| Redisモード | lag ≈ 0 |
| MemoryPollingモード（間隔 T 秒） | lag ∈ [0, T] |

**CDFによる可視化**: lag の累積分布関数（Cumulative Distribution Function）を描画することで，「p95のUAVがT秒以内に検知される」という性能保証の形で表現できる．

### 5.2 待機時間精度（補完指標）

```
waitingTime_polling ≈ waitingTime_redis + Δ_wait  (Δ_wait ∈ [0, T])
```

待機UAVの解除もポーリングサイクルで検知されるため，記録される待機時間にも同様の誤差が乗る．`flight_times.csv` の `waitingTime` 列で両モードを比較することで定量評価可能である．

### 5.3 測定精度とアーキテクチャの関係

| 測定項目 | Redis | MemoryPolling | 差の要因 |
|---|---|---|---|
| 飛行時間 | 連続時間で精密 | ±T秒の誤差 | 検知タイミングの離散性 |
| 待機時間 | 連続時間で精密 | ±T秒の誤差 | 解除タイミングの離散性 |
| 混雑率 | リアルタイム反映 | ポーリング周期で反映 | 状態更新の粒度 |

## 論文での論理展開

### 6.1 推奨する論述構造

```
[研究の問い]
  Redisによる疎結合アーキテクチャは，メモリ統合アーキテクチャと比べて
  どのような設計上・性能上のトレードオフをもたらすか？

[主張1: アーキテクチャ上の優位性]
  Redisモードは，SRP・DIP・疎結合の原則に基づいた設計であり，
  水平スケーラビリティ・外部観測可能性・分散展開適応性において優れる．

[主張2: 計測精度の制約]
  MemoryPollingモードは，ポーリング間隔 T に起因する検知遅延
  lag ∈ [0, T] を構造的に持つ．これは飛行時間・待機時間の
  計測精度に直接影響する．

[主張3: 機能的等価性の境界]
  インメモリイベント駆動モードはRedisモードと機能的に等価であり，
  Redisの利点は計算性能ではなくアーキテクチャ構造にある．

[結論]
  用途に応じた設計選択:
  - 実運用・スケールアウト → Redisモード
  - 研究実験（単一ホスト）→ MemoryEventDrivenモード
  - ポーリングラグの計測実験 → MemoryPollingモードとの比較
```

### 6.2 設計判断の正当化

「なぜ実験精度が同等のインメモリモードが存在するにもかかわらず，Redisアーキテクチャを主設計として採用したか」という査読者の問いに対しては，以下の論理で応答できる：

1. **実運用との整合性**: 実際のUAV管制システムでは，管制サーバと飛行シミュレーション環境が分離されることが一般的であり，Redisによる疎結合設計はその実運用アーキテクチャと構造的に対応する．

2. **拡張性の保証**: 複数の管制アルゴリズムを並列に評価する場合，Redisキューを共有することで，アーキテクチャ変更なしに並列実験が可能になる．

3. **計測の独立性**: OperatorとNetworkManagerが独立したコンポーネントとして動作するため，計測対象（経路探索時間，飛行時間）の独立性が保証される．
