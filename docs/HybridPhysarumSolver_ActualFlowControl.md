# HybridPhysarumSolver 実際のフロー制御ロジック

**作成日**: 2025-11-09  
**対象**: `src/server/route/HybridPhysarumSolverRouteSearcher.java`

## 概要

HybridPhysarumSolverのフロー制御ロジックのコード分析結果。設計仕様と実装の乖離を明らかにし、実際の動作を端的にまとめる。

## ⚠️ 重要な発見

**統合スコアチェックによるフロー減少は実質的に実行されない**

理由: if-else文の構造により、統合スコアの主要構成要素（ソース圧力関連）が先に個別チェックで処理されるため。

---

## フロー減少ケース

### 1. ソース圧力変化率による段階的減少 ⭐**メイン**

```java
changeRate = (現在圧力 - 前回圧力) / 前回圧力
```

| 変化率範囲 | UAV減少量 | 説明 |
|-----------|----------|------|
| 7% ≤ 変化率 < 12% | **1 UAV** | 軽微な圧力増加 |
| 12% ≤ 変化率 < 15% | **3 UAV** | 中程度の圧力増加 |
| 変化率 ≥ 15% | **5 UAV** | 重大な圧力増加 |

**特徴**:
- 圧力**増加時のみ**反応（低下時は無視）
- 猶予期間を無視して即座実行
- フロー減少後、50イテレーション猶予期間開始

### 2. ソース圧力絶対値による緊急減少（フロー半減）

| 圧力閾値 | UAV減少量 | 説明 |
|---------|----------|------|
| 圧力 ≥ 100.0 | **現在フロー / 2** | 緊急レベルの絶対圧力でフロー半減 |

**特徴**:
- 絶対値100.0以上で検知
- 猶予期間を無視して即座実行
- 現在のフロー値を半分にする動的減少
- フロー減少後、50イテレーション猶予期間開始

### 3. ~~統合スコアチェック~~ ❌**デッドコード**

**実行されない理由**:
```java
if (sourcePressureChangeScore >= 1.0) {          // ソース圧力変化率
    // フロー減少処理
} else if (sourcePressureScore >= 1.0) {         // ソース圧力絶対値  
    // フロー減少処理
} else if (iterationsSinceFlowChange < 50) {     // 猶予期間
    // スキップ
} else if (instabilityScore >= 5.0) {            // ⬅️ ここに到達しない
    // 統合スコア緊急
} else if (instabilityScore >= 3.0) {            // ⬅️ ここに到達しない
    // 統合スコア警告
}
```

**統合スコアの構成要素**:
- **ソース圧力スコア** (重み×3.0) → 上記2で先処理
- **ソース圧力変化率スコア** (重み×3.0) → 上記1で先処理
- 圧力勾配スコア (重み×2.5) → 残存
- 圧力絶対値スコア (重み×2.0) → 残存  
- チューブ厚変化率スコア (重み×1.5) → 残存

**結果**: 最高重み項目が既に処理済みのため、統合スコアは事実上機能しない

## フロー増加ケース

### 1. ソース圧力10%減少検知による増加 ⭐**唯一**

| 条件 | UAV増加量 | 制限 |
|------|----------|------|
| 現在圧力 < 基準圧力×0.9 **かつ** 現在フロー < 要求フロー | **1 UAV** | 要求フロー上限 |

**基準圧力の更新ロジック**:
- **フロー変更時**: 基準圧力をリセット
- **次回イテレーション**: 新しい現在フロー値での1イテレーション目圧力を基準として再キャプチャ

**動作例**:
```
現在フロー30での基準圧力: 45.0 → 10%減少閾値: 40.5
現在圧力: 35.0 → 増加実行（フロー30→31）
フロー31での新基準圧力: 38.0 → 10%減少閾値: 34.2
```

**制限事項**:
- 要求フロー以上では増加しない
- 「flow already at requested level」ログ出力
- フロー増加後は基準圧力リセット（`currentFlowBaselineCaptured = false`）

---

## 実行優先順位

```
1. ソース圧力絶対値チェック（100以上）   ← 即座実行（フロー半減）【最優先】
2. ソース圧力変化率チェック（7%/12%/15%）← 即座実行
3. ソース圧力10%減少チェック（増加）    ← 即座実行
4. 猶予期間チェック（50イテレーション） ← スキップ処理
5. 統合スコアチェック                  ← 実質デッドコード
```

---

## 最小フロー制約

```java
minimumFlow = max(1.0, requestedFlow × 0.1)  // 10%
```

**例**:
- 要求フロー 30 → 最小フロー 3.0
- 要求フロー 50 → 最小フロー 5.0

**制約到達時**: フロー減少拒否 → 安定カウント増加 → 収束促進

---

## 収束条件

- **収束判定**: 500回連続安定
- **安定とみなす条件**:
  - フロー減少トリガーなし
  - フロー減少が最小制約で拒否された場合

## 実装の問題点

### 1. 設計と実装の乖離
- **設計意図**: 複数指標の統合的監視
- **実際の動作**: ソース圧力のみの監視

### 2. デッドコード
- 統合スコア計算ロジックが大部分未使用
- 複雑な計算処理が無駄に実行

### 3. ドキュメント不整合
- 既存ドキュメントと実装で異なる仕様
- 最小フロー比率: ドキュメント70% vs 実装10%

---

## 改善提案

### Option 1: 統合スコアロジックの削除
- デッドコードを削除してシンプル化
- ソース圧力チェックのみに特化

### Option 2: if-else構造の修正
- 統合スコア優先の構造に変更
- 個別チェックを統合スコア内で実行

### Option 3: ドキュメント修正
- 実際の動作に合わせてドキュメント更新
- 設計意図の明確化
