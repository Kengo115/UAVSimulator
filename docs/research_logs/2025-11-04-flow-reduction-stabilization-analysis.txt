1. 問題の発見
================================================================================

【実行ログからの観察】
最大フロー30のネットワークに対して、要求フロー31で適応的フロー制御を実行した際、
フロー減少が連続的に発生し、最終的にフロー26まで過剰に減少する問題が発見された。

実際のログ（2025-11-03実行）:
```
Iteration 631 (flow=31): トレンド検知 (score=2.821) → flow 30に減少 ✓
Iteration 633 (flow=30): Early warning (score=3.040) → flow 29に減少 ✗
Iteration 634 (flow=29): Early warning (score=3.488) → flow 28に減少 ✗
Iteration 635 (flow=28): Early warning (score=3.295) → flow 27に減少 ✗
Iteration 636 (flow=27): Early warning (score=3.108) → flow 26に減少 ✗
```

【問題の深刻さ】
- 最大フロー30のネットワークで、フロー26まで減少（-4UAV、約13%の損失）
- フロー31→30への減少は正しい（最大フロー超過の検知）
- しかし、フロー30→29→28→27→26の連続減少は誤検知による過剰反応


================================================================================
2. 根本原因の分析
================================================================================

【技術的な原因】

問題の核心は「フロー変更直後の過渡的な不安定状態」の誤解釈にある。

(1) フロー変更直後の物理的挙動：
    - 圧力分布が大きく変動
    - チューブ厚が再調整される
    - 流量が新しいフロー値に収束していく過程

(2) 不安定性スコアの挙動：
    Iteration 631: flow 31→30に減少
    Iteration 632: flow 30, score=2.903（まだ高い）
    Iteration 633: flow 30, score=3.040（Early warning閾値3.0を超える）

    → この時点でのscore=3.040は「flow 30が不安定」ではなく、
       「flow 31→30への変更直後の過渡状態」を反映している

(3) 連鎖的な誤検知：
    flow 30→29への減少 → 再び過渡状態 → score高い → 29→28への減少
    → この悪循環が続く

【現在の不安定性検知ロジック】

```java
if (instabilityScore >= EMERGENCY_THRESHOLD) {        // score >= 5.0
    // 緊急対応：2UAV減少
    applyUAVFlowReduction(EMERGENCY_FLOW_REDUCTION_UAV, "Emergency instability");
} else if (instabilityScore >= EARLY_WARNING_THRESHOLD) {  // score >= 3.0
    // 早期警告：1UAV減少
    applyUAVFlowReduction(WARNING_FLOW_REDUCTION_UAV, "Early warning");
} else {
    // 安定：カウンター増加
    stableIterationCount++;
}
```

このロジックは「絶対値ベースの判定」のみで、以下を考慮していない：
- フロー変更後の経過時間
- システムの安定化に必要な時間
- 過渡的な高スコアと真の不安定性の区別

3. 検討した解決策
================================================================================

【解決策1: トレンドベース不安定性検知】（10/31に実装済み、その後削除）

アプローチ：
- スコアの履歴を記録（過去20イテレーション）
- 最小二乗法で傾き（増加率）を計算
- 増加率が閾値を超えたら不安定と判定

実装内容：
- SCORE_HISTORY_SIZE = 20
- MAX_ACCEPTABLE_SCORE_INCREASE_RATE = 0.08
- TREND_WARNING_THRESHOLD = 0.05
- MIN_ITERATION_FOR_TREND = 50

問題点：
- グローバルなイテレーション番号で判定していたため、フロー変更直後も
  トレンド検知が動作してしまう
- フロー変更時にスコア履歴がリセットされないため、過去の異なるフロー値での
  スコアがトレンド計算に影響


【解決策2: スコア履歴リセット機能】（11/4に検討）

アプローチ：
- フロー変更後の経過イテレーション数を追跡
- フロー変更時にスコア履歴を完全にリセット
- トレンド検知の条件を「フロー変更後の経過時間」で判定

実装内容：
```java
private int iterationsSinceFlowChange = 0;

private void resetScoreHistory() {
    scoreHistoryIndex = 0;
    scoreHistoryCount = 0;
    iterationsSinceFlowChange = 0;
}

// トレンド検知条件
if (iterationsSinceFlowChange < MIN_ITERATION_FOR_TREND) {
    return false; // フロー変更直後は安定化を待つ
}
```

問題点：
- トレンド検知の誤発火は防げるが、絶対値ベースの不安定性検知
  （Early warning, score >= 3.0）の誤発火は防げない


【解決策3: 安定化猶予期間の導入】（11/4に検討、推奨案）

アプローチ：
- フロー変更後、一定期間（例：50イテレーション）は「安定化猶予期間」とする
- 猶予期間中は**すべての不安定性検知を一時停止**
- システムが新しいフロー値で安定化する時間を確保

実装内容：
```java
private static final int STABILIZATION_GRACE_PERIOD = 50;

// メインループ
if (iterationsSinceFlowChange < STABILIZATION_GRACE_PERIOD) {
    // 安定化猶予期間中：不安定性検知をスキップ
    stableIterationCount++;
    consecutiveStableForIncrease++;

    // 定期的にログ出力
    if ((ct + 1) % 10 == 0) {
        LogManager.getInstance().log("Stabilization grace period: iteration " + (ct + 1) +
                                  " (" + iterationsSinceFlowChange + "/" + STABILIZATION_GRACE_PERIOD +
                                  ") with flow " + currentFlow +
                                  " (score: " + String.format("%.3f", instabilityScore) + ")");
    }
} else if (instabilityScore >= EMERGENCY_THRESHOLD) {
    // 猶予期間終了後：通常の不安定性検知を実行
    ...
}
```

期待される効果：
```
Iteration 631 (flow=31): 不安定性検知 → flow 30に減少 ✓
[スコア履歴リセット + iterationsSinceFlowChange = 0]

Iteration 632-681 (flow=30): 安定化猶予期間
  → 10イテレーションごとに "Stabilization grace period" ログ出力
  → 不安定性検知は一時停止、システムがflow 30で安定化

Iteration 682以降 (flow=30): 猶予期間終了、通常の不安定性検知再開
  → スコアが十分低下しているため、安定と判定
  → flow 30で安定収束 ✓（最大フローに到達）
```

6. 理論的考察
================================================================================

【Physarumアルゴリズムの動的特性】

Physarumアルゴリズムは以下の微分方程式に基づく：

dD_ij/dt = |Q_ij|^γ / (1 + |Q_ij|^γ) - μD_ij

ここで：
- D_ij: チューブ厚
- Q_ij: 流量
- γ: 非線形パラメータ（通常1.0-2.0）
- μ: 減衰係数（degeneracy effect）

【システムの時定数】

フロー変更後、システムが新しい平衡状態に到達するまでの時間は、
以下の要因に依存する：

1. チューブ厚の調整速度（DELTA_TIME）
2. 圧力分布の伝播速度（ネットワークトポロジー依存）
3. 流量の収束速度（非線形項の影響）

実験的観察から、安定化には約50-100イテレーションが必要と推定される。

【安定性判定の理論】

真の安定性判定には以下を考慮すべき：

1. 時間的要素：
   - 十分な観察期間（例：50イテレーション）
   - 連続的な安定状態の確認

2. 空間的要素：
   - ネットワーク全体の圧力分布の収束
   - チューブ厚の変化率の低下

3. トレンド要素：
   - スコアの時間的変化（増加/減少トレンド）
   - 振動の有無

**適応的な猶予期間長**

フロー減少量に応じて猶予期間を調整：
```java
private int calculateGracePeriod(double flowReduction) {
    if (flowReduction >= EMERGENCY_FLOW_REDUCTION_UAV) {
        return 100; // 大きな変更には長い猶予期間
    } else {
        return 50;  // 小さな変更には短い猶予期間
    }

```


【長期的な改善策（推奨度：低〜中）】

1. **多段階不安定性判定**

   → 3つのレベルで総合的に判定

2. **機械学習ベースの安定性予測**
   - 過去の実行データから学習
   - 現在のネットワーク状態から最適なフロー値を予測
   - ただし、実装コストとデータ収集が課題

- ネットワークサイズ
- ネットワークトポロジー（密/疎）
- フロー値の大きさ
- DELTA_TIMEの値

実験的に最適値を見つける必要がある。

【3. 緊急時の例外処理】

猶予期間中でも、極端な異常（例：solver failure）には対応すべき：
```java
if (iterationsSinceFlowChange < STABILIZATION_GRACE_PERIOD) {

    // 緊急時は猶予期間中でも対応

```
